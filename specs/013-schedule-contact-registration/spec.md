# 共有相手登録 現行仕様

**Status**: Current behavior contract

**Scope**: 事前登録された家族内での共有相手の申請、承認、呼び名、登録解除

## Authority Boundary

この文書は、共有相手登録の current product behavior と privacy boundary を所有する。
登録は二者の同意関係であり、予定の公開や編集権限そのものではない。
予定ごとの共有・閲覧・個別解除・自己離脱は
[Spec 012](../012-personal-schedule-sharing-privacy/spec.md) が所有する。

対象は本人と、オペレーターが明示的に事前登録した家族に限る。
account provisioning、public signup を提供しない境界、認証は
[Spec 009](../009-authentication-account-access/spec.md) のままである。
公演への Invitation は [Spec 006](../006-invitation-coordination-opacity/spec.md) の別概念であり、
その承認を共有相手登録へ流用しない。

画面の exact copy と presentation は runtime と tests、構造と手順は supporting artifacts が所有する。
申請先の解決方法、表、RPC、RLS、lock、移行の mechanics をこの仕様で再定義しない。

## User Scenarios & Testing

### Scenario 1: 初回に相手を指定して登録を申請する

利用者は相手の登録メールアドレス全体を入力して申請する。前後の空白と大文字小文字を正規化して
完全一致で扱い、部分一致や provider 固有の dot / plus alias 展開はしない。
申請者の申請意思と、相手本人の明示承認がそろって初めて登録が成立する。
自分自身との関係を作れず、同方向の重複申請や逆方向の申請だけでも承認は成立しない。

形式が正しい他人宛ての入力について、受付結果から未登録・既存申請・登録済み等を知らせない。
受付の案内は相手の存在、申請の作成、相手への到達を保証しない。
未登録の相手に account や外部向け申請、メールを作成・送信しない。

### Scenario 2: 自分宛ての申請へ回答する、または自分の申請を取り消す

利用者が確認・承認・拒否できるのは自分宛ての未解消の申請だけである。
承認判断に必要な申請者の登録メールと申請日時を確認できる。
申請者向けの送信済み一覧、対象の存在に依存する送信件数・badge、拒否履歴は提供しない。

申請者は申請時に入力した完全一致メールを指定して取り消せる。
相手のメールが後で変わっても元の入力で取消でき、相手の存在や実際の削除件数は知らせない。
拒否・取消は申請だけを解消する。解消済みの申請への古い承認、二重回答、承認と取消の競合で
重複した関係や古い関係を作らない。拒否・取消後の再申請は新しい同意サイクルであり、undo ではない。

### Scenario 3: 登録済みの相手を管理する

本人が参加する登録済み関係と、その相手の現在の登録メールを確認できる。
「妻」など自分用の呼び名を設定でき、空の値に戻せば自分の呼び名だけを取り除く。
呼び名は本人だけが閲覧・編集でき、相手や第三者に伝わらず、相手のプロフィールを変更しない。

登録だけでは予定を公開しない。共有する場合は、owner が登録済みの相手を選び、予定ごとに明示する。
登録や申請の identity は本人の account に結び付き、メール変更や旧メールの別 account による再利用で
関係・申請・既存共有が別人へ移転しない。

### Scenario 4: 登録を解除し、必要なら再登録する

どちらの当事者も登録を解除できる。解除は二者間の両方向の既存予定共有をすべて失効させ、
その関係の呼び名も除去する。予定本体や第三者への共有は残す。
個別の予定共有解除・recipient の自己離脱は当該共有だけを外し、登録関係を維持する。

解除と同じ登録世代への共有追加が競合しても、解除成立後にその世代の共有を残さない。
再登録は新しい関係であり、過去の共有や呼び名を自動復活させない。
古い登録・申請を参照する画面から再送しても、新しい同意を代替できない。

account が削除された場合、その人との申請・関係・呼び名・共有先としての共有は残さず、
他 owner の予定本体は消さない。削除された owner 自身の予定 lifecycle は
[Spec 007](../007-personal-schedule-lifecycle/spec.md) の責務である。

## Requirements

- **SCR-001**: 本人と事前登録家族の範囲を維持し、登録機能で利用資格や public signup を拡大しない。
- **SCR-002**: 初回の申請は正規化した完全一致メールだけで相手を指定し、一般検索や部分一致を提供しない。
- **SCR-003**: 申請者の意思とrecipient 本人の明示承認が必要で、自己申請、重複・逆向き申請だけで関係を作らない。
- **SCR-004**: 自分宛ての current pending だけ回答可能とする。拒否・取消・二重回答・古い承認で関係を復元しない。
- **SCR-005**: 申請・取消の受付結果から対象の存在や処理件数を開示せず、対象依存の送信一覧・件数・履歴を提供しない。
- **SCR-006**: 存在推測対策は返却本文だけでなく、直 API、エラー、header / Cookie、一覧、応答時間を対象にする。
  申請の試行制限は未登録・重複・no-op も存在非依存に数える。同じ受付結果だけを完全な時間差対策の証明と扱わない。
- **SCR-007**: 登録だけでは予定を公開せず、新規共有には有効な登録関係とowner の予定ごとの明示操作が必要である。
- **SCR-008**: 個別共有解除・自己離脱と登録解除を区別する。登録解除は二者間の全共有と呼び名だけを除去する。
- **SCR-009**: 登録解除と共有追加の競合でも、解除された同意世代からの共有を残さない。
  再登録は別の同意世代とし、過去の共有や呼び名を自動復活させない。
- **SCR-010**: 呼び名は本人だけが閲覧・編集できる。他人の申請・関係・呼び名や他recipient を第三者へ開示しない。
- **SCR-011**: メール変更・旧メール再利用で関係や共有を別 account へ移転しない。申請の取消は元の入力で可能とする。
- **SCR-012**: 既存共有から相互承認を自動生成せず、未承認の既存共有を移行のために自動失効させない。
- **SCR-013**: account 削除で相手所有の予定を削除しない。登録の解除と予定 lifecycle を混同しない。
- **SCR-014**: 利用可能性を確認できない場合は登録・管理・新規共有を利用可能や空の成功として扱わず、旧email共有へ戻さない。

## Cross-domain and Transition Boundary

- 予定のprivate default、閲覧のみの共有、個別解除・自己離脱、他recipient の秘匿、再読取時の表示は Spec 012 が所有する。
- 共有相手登録は公演 Invitation のpending coordination や予定ごとの承認ではない。
- 現在は新規共有の登録必須化を採用した段階である。登録導入前の既存共有を自動承認・一括失効させない。
  既存共有を登録世代へ一括移行し、すべての読取にその関係を必須とする後続段階は未採用である。
  現在の既存共有の可視性は Spec 012 の段階移行境界に従う。
- 移行・実機検証の手順と完了証跡は [段階移行runbook](../../docs/runbooks/schedule-contact-registration-rollout.md) と GitHub が所有する。

## Scope Boundaries

一般ユーザー検索、第三者への公開利用拡大、SNS、group、自動共有、登録リンク、外部メール送信、
account の自動作成、汎用プロフィール・連絡帳、恒久ブロック、拒否理由・履歴・undo は提供しない。
既に端末で閲覧・保存した内容を遠隔消去する機能も提供しない。

## Success Criteria

- **SC-001**: 相手本人の承認なしに登録が成立せず、登録だけでは予定が公開されないことを検証できる。
- **SC-002**: 自己・重複・逆向き・古い申請と承認/取消の競合を区別して検証できる。
- **SC-003**: 呼び名と他人の申請・関係の秘匿、存在非依存の受付と試行制限を検証できる。
- **SC-004**: 登録解除後の二者間共有と再登録による自動復活がなく、予定本体と第三者共有が残ることを検証できる。
- **SC-005**: メール変更・account 削除の本人境界と、未採用の既存共有移行を現在の機能から区別できる。
